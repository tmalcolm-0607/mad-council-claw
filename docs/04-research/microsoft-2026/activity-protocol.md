## Load-bearing patterns

### What Activity Protocol is

Verbatim from M365 Agents SDK:

> "Activity Protocol is a standard communication protocol used across Microsoft in many Microsoft SDKs, services, and clients. Activity Protocol is used by Microsoft 365 Copilot, Microsoft Copilot Studio, and the Microsoft 365 Agents SDK. Activity Protocol defines the structure of an `Activity` and how messages, events, and interactions flow from a channel to your code and everywhere else in between."

**Three M365 surfaces all speak Activity Protocol:**
1. Microsoft 365 Copilot
2. Microsoft Copilot Studio
3. Microsoft 365 Agents SDK

If our engine speaks Activity Protocol on its boundary, it can be invoked from all three.

### What an Activity is

> "An `Activity` is a structured JSON object that represents *any* interaction between a user and your agent. Activities aren't limited to text-based messages. They can include various types of interaction, such as events like a user joining or leaving for clients that support multiple users, typing indicators, file uploads, card actions, and custom events that developers design."

### Schema — key properties (verbatim table)

| Property | Description |
|---|---|
| `Id` | Typically generated by the channel if originating from a channel |
| `Type` | The type controls the meaning of an activity, for example message type |
| `ChannelID` | References the channel that the activity originated from (e.g., `msteams`) |
| `From` | The sender (user or agent) |
| `Recipient` | The intended recipient |
| `Text` | Text content of the message |
| `Attachment` | Rich content like cards, images, files |

### Activity types in use

| Type | Purpose |
|---|---|
| **Message** | Foundational communication (text/media/cards). User makes a query → agent responds. |
| **Event** | Asynchronous nonverbal trigger; user joining, context changes, custom application events |
| **Invoke** | Specific operation/command (Teams `task/fetch`, `task/submit`); not all channels support |
| **Typing** | Channel renders typing indicator; not supported on M365 Copilot |
| **Handoff** | External-channel control transfer (e.g., AudioCodes voice handoff) |
| **Conversation update** | User joined/left for multi-user clients |

### Channel-specific considerations (verbatim)

#### Microsoft Teams
- Rich Adaptive Cards with advanced features
- Message updates AND deletions
- Specific channel data for Teams features (mentions, meeting info)
- Invoke activities for task modules

#### Microsoft 365 Copilot
- **Primarily focused on message activities**
- Supports citations and references in responses
- **Requires streaming responses**
- Limited support for rich cards / adaptive cards

#### Web Chat / DirectLine
- Full support for all activity types
- Custom channel data

#### Non-Microsoft (Slack, Facebook, etc.)
- Limited activity-type support
- Card rendering varies / unsupported in some

### Sending events (Copilot Studio)

The **Event activity** node sends event activities. Set name + value (primitive / variable / Power Fx formula). Value serialized as JSON literal. Channel chooses if/how to use.

Use cases the docs name:
- Configure a custom Web Chat control to handle agent-emitted events
- Control AudioCodes recording services (start/stop call recording)

### Sending invoke (Teams-specific)

`Invoke activity` node sends Bot Framework Schema activity types. Common types:
- `Typing` — renders typing indicator
- `Invoke` / `Invoke response` — Teams task modules; topic with invoke trigger intercepts incoming Invoke
- `Handoff` — external channels (AudioCodes)

### Bringing existing agents to M365 Copilot

The 3-step pattern from `bring-agents-to-copilot`:
1. **Create app registration + Azure Bot Service record** to handle channel communication
2. **Configure agent event listeners** — `OnActivity` is the universal entrypoint. Agent listens for any message via `OnActivity`; the existing agent logic runs in the method triggered by the event
3. **Create manifest file** — `.zip` with manifest describing where Copilot can find the agent + app registration ID

Recommended starting point: M365 Agents Toolkit + Echo/Empty Agent sample (C# in Visual Studio, JavaScript in VS Code).

### Channel-data inspection

> "Channels include specific data that doesn't conform to the generic Activity payload across all channels. You can access this data from the `TurnContext.Activity.ChannelData` property by casting it to variables for use in your code."

### Hub architecture

> "The Microsoft 365 Agents SDK is built as a 'Hub' that developers use to create agents that can work with *any* client, including the clients we support. It provides the tools for developers to build their own channel adapter using the same framework. This architecture gives developers breadth when it comes to agents, and provides extensibility to clients to connect to that hub."

## Verbatim quotes worth preserving

> "Activity Protocol standardizes the communication protocol with any client you're working with, including Microsoft and non-Microsoft clients, so that you don't have to create custom logic for each channel."

> "Microsoft 365 Copilot ... requires streaming responses." (load-bearing: any engine endpoint targeting M365 Copilot must support streaming)

## Implications for the engine catalog (refs F-NNN)

- **F-activity-protocol-endpoint** — engine exposes an Activity Protocol endpoint as one of its standard outputs. A single endpoint accepts message/event/invoke/typing/handoff and routes to the appropriate workflow.
- **F-streaming-responses** — for any M365-Copilot-bound interaction, engine MUST stream. Enforce via SKILL contract and gate.
- **F-channel-adapter-pattern** — engine ships channel adapters (Teams / M365 Copilot / Web Chat / DirectLine / Slack / Discord / custom). Each adapter handles channel-specific data + capability differences.
- **F-onactivity-universal-listener** — engine's main event handler is OnActivity-style (listen-anything, dispatch by Activity.Type). Maps cleanly to our council-post message types.
- **F-channel-data-inspection** — engine's incoming-message handler always inspects ChannelData for channel-specific affordances (Teams mentions, meeting context, etc.) before processing.

## NEW F-NNN candidates (if any)

- **F-NEW: activity-protocol-bridge** — bidirectional bridge: engine messages ↔ Activity Protocol activities. Engine workflows callable from Teams/Outlook/M365 Copilot via a single bridge component.
- **F-NEW: hub-pattern** — adopt M365 Agents SDK "Hub" pattern as engine's multi-channel architecture. One core engine + N channel adapters that translate to/from Activity.

## Confidence

**HIGH** — Activity Protocol is documented in three orthogonal places (M365 Agents SDK, Copilot Studio, M365 Copilot extensibility) and the spec is open-source on GitHub (`microsoft/Agents/specs/activity/protocol-activity.md`). The "Hub" architecture, OnActivity entrypoint, and channel-specific affordances are all verbatim from the M365 Agents SDK page. The 3-step "bring agents to Copilot" pattern is the official onboarding path. No "preview" caveats apply — Activity Protocol is foundational and stable.
