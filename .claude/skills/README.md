## Workflow

The typical MAD workflow follows this sequence:

### Core Specification Workflow

1. **Specify**: Create the feature specification from natural language
   - **NEW**: Includes Source Coverage Validation to ensure ALL workflows from source documents are captured
2. **Checklist (source-coverage)**: Generate source coverage checklist FIRST when source documents exist
   - **CRITICAL**: Prevents missing workflows by validating spec against idea documents
3. **Plan**: Generate technical design artifacts from the spec
4. **Tasks**: Break down the plan into actionable tasks
5. **Checklist** (optional): Generate domain-specific requirement quality checklists (UX, API, Security)
6. **Implement**: Execute the tasks phase-by-phase
7. **Automation**: Validate specification quality and sync with implementation

### Source Coverage Validation (NEW)

**Problem Solved**: In the past, 5 critical workflows were missed during specification because the idea document wasn't systematically checked for completeness.

**Solution**: The `mad-spec` skill now includes a mandatory Source Coverage Validation phase:
- Extracts ALL workflows from referenced source documents
- Cross-references against generated user stories
- Reports gaps and requires resolution before proceeding

**Best Practice**: After running `mad-spec`, run `mad-checklist source-coverage` to generate a dedicated checklist validating that all source material is represented in the spec.

- **cosmos-provisioning**: Provision Cosmos DB containers with partition keys and indexing
- **e2e-test-aci**: Run behavioral E2E tests via Azure Container Instances

## Key Concepts

### Technology-Agnostic Specifications
Specifications focus on WHAT users need and WHY, not HOW to implement. They avoid tech stack, APIs, and code structure, making them accessible to business stakeholders.

### Constitutional Constraints
The `.mad/memory/constitution.md` file defines architecture principles and constraints that all implementations must follow. The plan phase validates against these constraints.

### User Story Organization
Tasks are organized by user story (P1, P2, P3...) to enable independent implementation and testing. Each story becomes a complete, testable increment.

### Quality Gates
Implementation includes mandatory quality gates after each phase:
- Automated validation (lint, typecheck, format)
- Test execution (unit + integration)
- Manual checks (anti-patterns, error handling)
- Atomic commits

### Requirements Quality Checklists
Checklists are "unit tests for English" - they validate requirement quality (completeness, clarity, consistency, measurability, coverage) rather than implementation correctness.
