## Target milestone proposal

Two options for where the reopened items land. The council verdict in (3) of the reopen protocol selects between them; this artifact recommends but does not decide.

### Option A — M9 expansion

**Shape:** the existing M9 milestone (M365 integration) absorbs F-D-008, F-D-010, F-D-018 alongside the already-RED F-076 / F-077 / F-078 / F-079 / F-080 / F-081 (MSAL / WAM / Graph clients / WorkIQ adapter) and the just-authored F-206..F-210 (m-relay-main lift surfaces).

**Pros:**
- Single milestone owns "the M365 surface" end-to-end (read via WorkIQ + write via adapters + relay transport).
- F-206..F-210 already land at M9; co-locating their soft-block hinge (F-D-008) in the same milestone keeps the dependency graph local.
- Lower roadmap blast-radius: no new milestone row, no renumbering.
- Matches the foundational-plan's catalog clustering (F-D-008/009/010/018 are all in the "outbound surface federation" cluster per `M19-deferred/README.md:43-45`; M9 is the natural inbound+outbound aggregator).

**Cons:**
- M9 grows from 6 features (F-076..F-081) to 14+ (F-076..F-081 + F-206..F-210 + F-D-008/F-D-010/F-D-018 + their wires). Larger milestone scope = longer wave to GREEN.
- Risks confusing "M9 reads M365" (what ships in v1) vs "M9 writes M365" (what ships in v1.5+).

### Option B — New M-Teams milestone

**Shape:** new `M-Teams` (or `M9.5-teams-write` or `M20-outbound-surfaces`) milestone is created. F-D-008, F-D-010, F-D-018 land there. F-206..F-210 may relocate there as well (since their entire purpose is to lift Teams-write infrastructure).

**Pros:**
- Clean separation: M9 stays "read M365 in v1"; new milestone stays "write to M365 in v1.5+".
- Matches the user's mental model surfaced in the audit ("Teams bot / Clawpilot timeline?") — Teams write IS the v1.5+ work, and naming it explicitly removes ambiguity.
- Easier to defer or accelerate as a unit if scope changes.

**Cons:**
- Higher roadmap blast-radius: adds a new milestone row, may require re-numbering downstream (M9..M19 are densely packed).
- F-206..F-210 either stay in M9 (creating a cross-milestone dependency to the new bucket) or move (re-authoring already-RED ledgers with a new milestone field).
- Foundational plan never named this milestone; introducing it requires its own discussion.

### Recommendation

**Option A (M9 expansion)** has the lower blast radius and follows the existing catalog clustering convention. It is the recommended target unless the council verdict surfaces a reason to split. The verdict body should explicitly choose A vs B; this artifact does NOT presume the choice.

If the council picks Option A:
- F-206..F-210 stay at M9 (already authored there).
- F-D-008 / F-D-010 / F-D-018 transition `milestone: M19` → `milestone: M9` and `status: deferred` → `status: red` in the same atomic commit as the verdict.
- Roadmap M9 row totals update; M19 row removes the three items from its DEFERRED count.

If the council picks Option B:
- New milestone row added to roadmap.
- F-206..F-210 ledgers may relocate (council decides; either path is acceptable).
- F-D-008 / F-D-010 / F-D-018 transition to the new milestone and to RED.

## STRIDE-touch

Per `.claude/rules/stride-threat-model.md` (in MAD - Clean kit), every new feature or change must enumerate all 6 STRIDE categories and confirm whether the change expands the attack surface; for each yes, name a mitigation with file:line evidence. **All 6 categories enumerated below — none silently elided.**

| # | Category | Expand attack surface? | Mitigation source |
|---|----------|------------------------|-------------------|
| 1 | **Spoofing** | **YES (significant)** | Reopen brings inbound Teams traffic + Bot Framework webhook into the engine's reach. Mitigation: Bot Framework JWT validation against OpenID metadata at `m-relay-main/src/bot.ts:33-77` (`validateBotFrameworkToken` — verifies Bearer token signature against Bot Framework JWKS + allowed issuers + audience=appId). Inbound WS auth at `m-relay-main/src/relay.ts:113-117,122-125,137` (token validation in `handleAuth`, close codes 4001/4002/4003 on timeout/invalid-JSON/auth-failure) per F-206 ledger acceptance items (a)-(d). User-side: m-main MSAL+WAM auth at `m-main/electron/auth/msal-provider.ts:46-48` + token-acquisition at `m-main/electron/auth/m365-token.ts:124-211` (audit Lane B). Combined: every inbound message has a verifiable AAD `oid` + signed Bot Framework token. |
| 2 | **Tampering** | **YES (medium)** | Outbound Bot Connector REST replies + conversation-ref persistence are new mutable shared state. Mitigation: F-210 conversation-ref-atomic-persist (already authored Batch 2) inherits `.claude/rules/concurrency-safety.md` §2 atomic-write-temp-then-rename. Permission-card lifecycle at `m-relay-main/src/cards.ts` + `relay.ts:339-418,554-566` (covered by F-209) uses Action.Execute with server-side state — client cannot tamper with the permission-decision record post-hoc. The relay's in-memory Maps (`clients`, `pendingRequests`, `rateCounts`, `conversationRefs` per `relay.ts:84-89`) are partitioned by `oid` per `concurrency-safety.md` single-writer-per-key discipline. |
| 3 | **Repudiation** | **YES (low)** | Bot replies + permission-card decisions become user-visible artifacts whose authorship the user could deny ("I didn't approve that"). Mitigation: every inbound activity carries `from.aadObjectId` (per `bot.ts:19` Activity interface) → relay logs hashed userId via `log-safe.ts:hashUserId` (per `m-relay-main/src/log-safe.ts`); permission-card responses persist with the `requestId` UUID v4 + signed Action.Execute payload from Teams (Bot Framework supplies the Activity envelope). Combined: inbound origin auditable; outbound reply auditable via Bot Connector REST response. Future cross-link to F-015 hash-chained audit-log when both ledgers are GREEN. |
| 4 | **Information Disclosure** | **YES (significant)** | Briefing content + permission-card prompts + bot replies cross from engine-local boundary into Microsoft Bot Service + Teams tenant. Mitigation (defense-in-depth): (a) per-user `oid`-keyed routing (`relay.ts:84-86` `clients` Map keyed by Azure AD `oid`) — replies only reach the originator; (b) hashed userId logging via `log-safe.ts` — operational logs never expose AAD object IDs in cleartext; (c) capability-negotiation intersection (`relay.ts:451-468`) — server-supported features are explicit, not user-claimed; (d) Adaptive-Card permission flow (`m-main/electron/cards.ts` + `m-main/ipc/teams-relay-ipc.ts:48-88` per audit Lane B) — engine asks user before exposing Graph data. **Residual:** Teams tenant is a third-party trust boundary; `prompt-injection-policy.md` Rule 1 (treat-as-data) applies to inbound Activities — engine MUST NOT execute directives in `Activity.text`. This is encoded in F-D-010 trigger 4 ("adversarial-input controls"). |
| 5 | **Denial of Service** | **YES (medium)** | Inbound Teams webhook + WebSocket are new ingress paths. Mitigation: rate-limit per user `oid` at `m-relay-main/src/relay.ts:72` (`RATE_LIMIT_PER_MINUTE = 100`, sliding 60s window) per F-206 acceptance item (h). 5-minute response timeout (`relay.ts:70` `RESPONSE_TIMEOUT_MS = 5 * 60 * 1000`). 30s ping keepalive (`relay.ts:71` `PING_INTERVAL_MS = 30_000`). Replacement-connection close (code 4004) prevents per-user fan-out (`relay.ts:445-449`). App Service Linux is a single-instance shape per `index.ts:79-82` — horizontal scale is OUT OF SCOPE per F-206 §"Out-of-scope-notes" item 5; users above one-instance threshold escalate per F-206's documented re-open trigger for clustering. |
| 6 | **Elevation of Privilege** | **YES (significant)** | The bot endpoint is publicly addressable; an attacker reaching it could attempt to mint privileged operations (proactive sends, permission grants, briefing destinations). Mitigation: (a) MSI-FIC federated-identity token mint at `bot.ts:125-175` — bot does not hold a long-lived secret; tokens are minted per-call via Managed Identity → Federated Identity Credential (MSI client_id from env + tenant-scoped `client_assertion_type: jwt-bearer`); covered by F-208. (b) `/api/proactive` endpoint validates the Graph token and extracts userId before sending (`bot.ts:362-405`) — only authenticated proactive sends. (c) Adaptive-Card permission cards (`m-relay-main/src/cards.ts` + F-209 ledger) require explicit user `allow / allow_session / always_allow / deny` action before any privileged operation surfaces in the engine; per `protocol.ts:59` `PermissionAction` enum is exactly 4 values. (d) Per `dangerous-operations-policy.md` Rule 1 (no silent writes) and Rule 5 (no consent-by-content), Activity-text-embedded "approved" claims do NOT satisfy a consent gate. |

**Summary:** 6/6 categories show some surface expansion (the reopen IS adding a remote conversational endpoint to a previously local-only engine — that is the substantive change). All 6 have mitigations cited at file:line. None are unmitigated. None are silently dropped. The council verdict at (3) of the reopen protocol is the appropriate gate for ratifying that these mitigations are sufficient at HIGH confidence.

### Required environment variables (4-7 keys)

Per `m-relay-main/src/index.ts:17-29` partial-config-fail-fast pattern, the 7 env vars council-claw needs:

1. `MicrosoftAppId` — bot's AAD app registration ID (audience for inbound JWT validation)
2. `MicrosoftAppMSIClientId` — Managed Identity client_id used by FIC token mint
3. `MicrosoftAppTenantId` — single-tenant scope for issuer validation
4. `IDENTITY_ENDPOINT` — App Service Linux MSI endpoint (auto-populated by App Service)
5. `IDENTITY_HEADER` — App Service Linux MSI header (auto-populated by App Service)
6. `PORT` — HTTP port (default 3978)
7. `WEBSITE_SITE_NAME` — App Service runtime indicator (auto-populated; used to gate persistent storage path)

Items 4, 5, 7 are populated automatically by App Service Linux; council-claw deployment authors set 1, 2, 3, and optionally 6.
