# AFD WAF Rules 200002 & 200003 — Technical Reference

## What These Rules Do

Rules 200002 and 200003 are part of the **General** rule group in `Microsoft_DefaultRuleSet` (all versions including 2.1). They are request body inspection validators — not attack pattern detectors.

| Rule ID | Name | Severity | Trigger Condition |
|---------|------|----------|-------------------|
| **200002** | Failed to parse request body | **Critical (score=5)** | WAF cannot fully parse the request body because it exceeds the 128KB body inspection limit. Adds 5 to anomaly score — enough to block alone. |
| **200003** | Multipart request body failed strict validation | **Critical (score=5)** | The `multipart/form-data` encoding fails the WAF's strict validation checks — typically because the multipart boundary or content length exceeds the inspection limit. Adds 5 to anomaly score — enough to block alone. |

## Why They Block File Uploads

Azure Front Door WAF inspects request bodies up to a **fixed 128KB limit**:
- **AFD WAF**: 128KB — **not configurable**. There is no `requestBodyInspectLimitInKB` property on AFD WAF.
- **Application Gateway WAF** (CRS 3.2+): Configurable up to 2MB via `requestBodyInspectLimitInKB`. This property does NOT exist on AFD.

When a file upload exceeds 128KB (e.g., a 15MB PDF), the WAF cannot fully parse the request body. Either rule 200002 or 200003 (or both) fire. **Each rule is Critical severity (anomaly score = 5), and the DRS 2.1 blocking threshold is also 5 — meaning a single trigger of either rule alone is sufficient to block the request.** Rule **949110** ("Inbound Anomaly Score Exceeded") then returns **HTTP 403** to the client.

Key characteristics:
- The 403 is returned at the **CDN edge** — the request never reaches the application backend
- **Application Insights** does not capture these blocks (only requests reaching the app are logged)
- The response body contains WAF-specific error details, but most frontends only read the HTTP status code
- Even if the inspection limit could be raised (it can't on AFD), 25-50MB uploads far exceed any WAF inspection capacity

## Incident Context

On March 25-26, 2026, 3 external law enforcement users were unable to submit preservation requests (2703(f)) on LE Portal beta. Users completed all 7 steps of the request wizard but received "Submission Error — API error status: 403" upon submission. Root cause: rules 200002 + 200003 in Prevention mode with empty `ruleGroupOverrides`.

## Why Disabling Is Safe (For Upload Services)

Rules 200002/200003 flag requests where the WAF **cannot fully inspect the body** due to the size limit. They do not detect specific attack patterns. Disabling them is safe for services that:

1. Have their own defense-in-depth:
   - JWT authentication (MSAL/MISE)
   - Authorization policies (tenant + application validation)
   - Input validation on all request models
   - File type/size validation at the application layer
2. Store uploads via Azure Blob Storage with SAS URIs (no direct file system access)
3. Have anti-malware scanning at the storage layer (Defender for Storage)

## Why NOT to Disable for Non-Upload Services

For services that do NOT accept file uploads >128KB, these rules provide value by:
- Detecting abnormally large request bodies (potential DoS or data exfiltration)
- Enforcing strict multipart validation (malformed multipart can carry injection payloads)
- Contributing to anomaly scoring that catches multi-vector attacks

**Only disable for services with confirmed file upload requirements.**

## Remediation Pattern

### Bicep — Disable in `ruleGroupOverrides`

Replace empty `ruleGroupOverrides: []` in the `Microsoft_DefaultRuleSet` entry with:

```bicep
ruleGroupOverrides: [
  {
    ruleGroupName: 'General'
    rules: [
      {
        ruleId: '200002'
        enabledState: 'Disabled'
      }
      {
        ruleId: '200003'
        enabledState: 'Disabled'
      }
    ]
  }
]
```

**Note on `action` field**: The `action` field (e.g., `'AnomalyScoring'`, `'Block'`, `'Log'`) is **not required** when `enabledState: 'Disabled'` — the action is ignored for disabled rules. Omitting it avoids schema validation differences across API versions:
- `@2024-02-01` accepts: `Allow`, `Block`, `Log`, `Redirect`, `AnomalyScoring`, `JSChallenge`
- `@2025-03-01` may have different valid values
- Omitting the field is safe across all versions when the rule is disabled

### Azure Portal — Manual Override

If immediate mitigation is needed before a Bicep deployment:
1. Azure Portal > Front Door > WAF Policy
2. Settings > Managed rules > General rule group
3. Rule 200002 > Disabled
4. Rule 200003 > Disabled
5. Save

**Warning**: Manual Portal changes are NOT reflected in Bicep templates. The next Bicep deployment will **re-enable these rules**, causing regression. Always follow up with a Bicep template fix.

## API Version Compatibility

| API Version | `enabledState: 'Disabled'` | `action` field | Notes |
|-------------|---------------------------|----------------|-------|
| `2024-02-01` | Supported | Optional when disabled | Used by LENS-LEPortal, LENS-LRMS |

## Alternative Remediation Architectures

### Architecture A — Blanket `ruleGroupOverrides` Disable (RECOMMENDED)

Disable rules 200002/200003 globally in the WAF policy via `ruleGroupOverrides`. This is what the `waf-audit` skill generates by default.

**What all endpoints keep**: Full DRS 2.1 protection (SQLi, XSS, bot protection, all other rules)
**What all endpoints lose**: Body-inspection-exceeded detection (rules 200002/200003)

**Why this is recommended**:
- Simple, proven, Microsoft-recommended approach (per Microsoft Q&A and documentation)
- All LENS services have defense-in-depth: MSAL/MISE auth, authorization policies, input validation, file type/size checks, Defender for Storage
- Rules 200002/200003 detect that the WAF *couldn't fully inspect* a body — they don't detect specific attack patterns. Disabling them doesn't remove SQLi/XSS/bot detection.
- Zero maintenance — no pattern lists to update when endpoints change

### Architecture B — Custom Allow Rules for Upload Paths (ADVANCED ALTERNATIVE)

Keep 200002/200003 ENABLED in managed rules. Add custom `Allow` rules matching upload URL paths (e.g., `RequestUri Contains 'upload'`). Custom rules evaluate before managed rules; `Allow` action exits evaluation, bypassing all managed rules for matching requests.

```
Priority 50:  RateLimitByIP        → Block (existing, fires first)
Priority 100: AllowUploadPaths     → Allow (RequestUri Contains 'upload')
              ↓ (only non-upload paths reach managed rules)
              DRS 2.1 with 200002/200003 ENABLED
```

**What upload paths keep**: Rate limiting (custom rule, higher priority)
**What upload paths lose**: ALL managed rule protection (SQLi, XSS, bot detection — not just 200002/200003)
**What non-upload paths keep**: Full DRS 2.1 INCLUDING 200002/200003

**Trade-off analysis**: Architecture B gives better security on non-upload paths (200002/200003 active) but worse security on upload paths (no managed rules at all). For LENS services, this trade-off is **not favorable** because:
- Upload endpoints receive binary file content — SQLi/XSS patterns in PDF bytes are false positives, so managed rule value on upload paths is low
- But losing ALL managed rules (not just 200002/200003) on upload paths is a larger security surface reduction than Architecture A's blanket disable
- Requires maintenance when upload routes change
- Non-"upload"-named endpoints (e.g., `/internationalReview/approve/{id}`) need additional Allow rules

**Use Architecture B only if**: Your threat model specifically requires 200002/200003 active on non-upload paths AND you accept the trade-off of no managed rules on upload paths.

### Architecture C — Dual WAF Policies + Scoped Security Policies (UNVALIDATED)

Theoretically, create two WAF policies (strict + relaxed) and two security policies with different `patternsToMatch`. The upload-specific security policy points to the relaxed WAF policy; the catch-all points to the strict policy.

**Status**: NOT validated in PPE. Azure documentation does not confirm that overlapping `patternsToMatch` between security policies is supported. Middle wildcards in patterns (e.g., `/api/v1/*/uploadFile`) may not work as expected. **Do not implement without PPE validation.**

## AFD WAF vs Application Gateway WAF — Key Differences for File Uploads

| Dimension | AFD WAF | Application Gateway WAF (CRS 3.2+ / DRS 2.1) |
|-----------|---------|-----------------------------------------------|
| Body inspection limit | **128KB fixed** — not configurable | Configurable up to 2MB via `requestBodyInspectLimitInKB` |
| `requestBodyInspectLimitInKB` | **Does not exist** | Supported — set in `policySettings` |
| `requestBodyEnforcement` toggle | **Does not exist** | Supported — can disable body size enforcement independently |
| `fileUploadEnforcement` toggle | **Does not exist** | Supported |
| Exclusion `matchVariable` values | RequestHeaderNames, RequestCookieNames, RequestBodyPostArgNames, RequestBodyJsonArgNames, QueryStringArgNames | Broader set (includes `RequestArgNames` and others) — **no `RequestUri` on either platform** |
| Per-rule scoping within a single WAF policy | **Not supported** — rule overrides apply to all traffic | **Not supported** — same limitation |
| Per-path WAF policy association | Via `securityPolicies` with `patternsToMatch` (unvalidated for overlapping patterns) | Supported — per-listener and per-URI WAF policy binding |
| Custom rule `RequestUri` matching | Supported (Allow/Block/Log/Redirect) | Supported |
| Custom rule `Allow` behavior | Bypasses ALL managed rules | Bypasses ALL managed rules |
| Managed rule set | DRS 2.1 (Microsoft_DefaultRuleSet) | CRS 3.2 or DRS 2.1 |
| Rules 200002/200003 severity (when using DRS) | Critical (score=5), single trigger blocks | Critical (score=5), single trigger blocks |
